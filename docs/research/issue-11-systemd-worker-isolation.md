# systemd worker isolation research for issue #11

This note uses the upstream systemd v259.8 man-page sources, systemd source, the kernel cgroup v2 documentation, and freedesktop.org journal documentation. It does not use secondary explanations.

## Contract and repository fit

Issue #1 is the accepted parent contract. It separates a system hardware broker, a per-user supervisor, and disposable Lua workers. It also requires ordinary user environment access, no broker device authority, a two-second Lua callback deadline, a 500 ms graceful-stop deadline, descendant cleanup, resource limits, and separate user/system journals. [Issue #1](https://github.com/wawow830/sliver/issues/1) [Issue #11](https://github.com/wawow830/sliver/issues/11)

The current tree has not crossed that process boundary yet. `supervisor_main()` constructs the M2 hardware adapter and the supervisor in one process, while `LuaWorker` runs the Lua owner as a Rust thread and hands frames through in-process shared state. The worker limit cannot be made reliable by adding a timer around the existing thread call. A separate worker process, with an external supervisor able to kill its unit, is required. [current supervisor entry point](https://github.com/wawow830/sliver/blob/ad3725a/crates/sliverd/src/lib.rs#L27-L83) [current Lua owner thread](https://github.com/wawow830/sliver/blob/ad3725a/crates/sliverd/src/lua_worker.rs#L284-L314)

## Sourced facts

### cgroup v2 and descendant accounting

The cgroup v2 hierarchy assigns every process to one cgroup. A forked process starts in its parent's cgroup, all threads of a process remain in one cgroup, and controller restrictions apply hierarchically to the inclusive sub-hierarchy. A child cgroup cannot override a stricter ancestor restriction. [kernel cgroup v2 documentation](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#what-is-cgroup)

`MemoryMax=` maps to the cgroup v2 `memory.max` hard limit. `memory.current` reports memory used by the cgroup and its descendants. Reaching `memory.max` can invoke the cgroup OOM killer, although the kernel documents temporary overage and allocation cases that do not invoke the OOM killer. `MemorySwapMax=` controls swap separately. [systemd.resource-control(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.resource-control.xml) [kernel memory interface](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#memory-interface-files)

`TasksMax=` maps to `pids.max`. systemd counts kernel threads and userspace processes, with each thread counted individually. The kernel pids controller counts TIDs, and `pids.current` includes the cgroup and its descendants. Fork and clone fail with `EAGAIN` when creating another task would violate the policy. The count is therefore 64 tasks, not necessarily 64 process IDs with one thread each. [systemd.resource-control(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.resource-control.xml) [kernel PID controller](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#pid)

The kernel's `cgroup.kill` file exists on non-root cgroups. Writing `1` kills the cgroup and all descendant cgroups with `SIGKILL`; the kernel handles concurrent forks and protects the operation against migrations. [kernel cgroup v2 core interface](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#cgroup-core-interface-files)

systemd v259 uses `cgroup.kill` for a requested `SIGKILL` when the kernel provides it, and falls back to recursive process enumeration when it does not. The systemd D-Bus `KillUnit()` operation can therefore provide a manager-owned final kill without giving the worker write access to cgroup files. [systemd unit kill source](https://github.com/systemd/systemd/blob/v259.8/src/core/unit.c#L4110-L4191) [systemd cgroup utility source](https://github.com/systemd/systemd/blob/v259.8/src/basic/cgroup-util.c#L219-L455)

`OOMPolicy=kill` tells systemd to set `memory.oom.group=1` so that an OOM kill takes the remaining processes in the unit and its descendant cgroups with it. The kernel describes that setting as an all-or-nothing cgroup workload kill, subject to its documented OOM-protection exception. [systemd.service(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.service.xml) [kernel memory interface](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#memory-interface-files)

### Unit topologies

A service unit is started and managed by the service manager. A transient service created with `StartTransientUnit()` is released after it is no longer running or referenced. The service manager starts the service in a clean, detached execution environment, with the manager as its parent. [systemd-run(1)](https://github.com/systemd/systemd/blob/v259.8/man/systemd-run.xml) [systemd D-Bus API](https://github.com/systemd/systemd/blob/v259.8/man/org.freedesktop.systemd1.xml)

A scope unit groups processes that an external process created. It has no main process, its state follows whether any process remains in the scope, and it does not start the worker itself. A scope's processes normally remain children of the external creator, which must collect their exit statuses. [systemd.scope(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.scope.xml)

The `systemd-run --scope` path inherits the caller's execution environment. The service path instead runs the command through the service manager in a clean, detached environment. [systemd-run(1)](https://github.com/systemd/systemd/blob/v259.8/man/systemd-run.xml)

A template service is a persistent unit definition whose instance name is inserted after `@`; `%i` exposes that instance name to the unit. Instanced services receive a per-template slice by default. [systemd.service(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.service.xml) [systemd.unit(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.unit.xml)

A delegated service or scope owns a private cgroup sub-hierarchy below its unit. systemd stops managing that subtree, and an unprivileged unit's cgroup is made accessible to the configured user. Delegation is the explicit single-writer boundary for applications that manipulate cgroup files themselves. [systemd.resource-control(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.resource-control.xml) [systemd control group delegation](https://systemd.io/CGROUP_DELEGATION) [kernel delegation model](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#delegation)

Transient properties and administrator drop-ins are compatible. systemd's source deliberately does not reject drop-ins when deciding whether a unit is pristine enough to become transient. Unit-specific and hierarchical drop-ins are then parsed after the unit fragment. [systemd unit source](https://github.com/systemd/systemd/blob/v259.8/src/core/unit.c#L5250-L5266) [systemd.unit(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.unit.xml)

Drop-in lookup supports truncated names at dash boundaries. For a generated name such as `sliver-lua-worker-abc123.service`, `sliver-lua-worker-.service.d/*.conf` is a usable common drop-in path. Drop-ins are merged in lexical order, and the administrator's system paths are ordered separately from user configuration paths. [systemd.unit(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.unit.xml)

The following table distinguishes what a user service can request from what the setting guarantees. "User service" means a unit managed by `systemd --user`, not a system unit whose `User=` happens to name a login user.

| `MemoryMax=512M` | Supported. `MemoryMax` is a cgroup resource setting, and the user manager manages a delegated subtree below `user@UID.service`. | It writes `memory.max`; the effective limit is the most stringent limit from the unit and its parent slices. It includes memory charged to descendant cgroups, but is not an instantaneous byte-for-byte wall under every kernel allocation path. [systemd.resource-control(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.resource-control.xml) [user@.service(5)](https://github.com/systemd/systemd/blob/v259.8/man/user@.service.xml) [kernel cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#memory-interface-files) |

[systemd.resource-control(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.resource-control.xml) [kernel PID controller](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#pid) |

[systemd.service(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.service.xml) [systemd service D-Bus source](https://github.com/systemd/systemd/blob/v259.8/src/core/dbus-service.c#L584-L610) |
| `NoNewPrivileges=yes` | Supported for user services and transient services. | It prevents the service and directly or indirectly forked children from gaining privilege through `execve()`, including setuid bits and file capabilities. It does not stop a worker from asking an already privileged or separately managed process to do something through IPC. [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml) [transient exec-property source](https://github.com/systemd/systemd/blob/v259.8/src/core/dbus-execute.c#L2274-L2293) |
| `PrivateDevices=yes` | Supported in a user service only with the user-namespace condition documented by systemd. systemd implicitly enables `PrivateUsers=` in this case, and the kernel must permit unprivileged user namespaces. | It gives the worker a new `/dev` containing API pseudo-devices and pseudo-TTY support, not physical devices. It also sets `DevicePolicy=closed`, removes `CAP_MKNOD` and `CAP_SYS_RAWIO`, and blocks the `@raw-io` system-call group. systemd warns that the namespace implementation may be unavailable and should not be the only security check. [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml) [systemd user-namespace condition](https://github.com/systemd/systemd/blob/v259.8/man/system-or-user-ns.xml) |
| `DevicePolicy=closed` or `strict` | A cgroup resource setting accepted by the user manager when the device controller and systemd's device filtering support are available. | `closed` permits standard pseudo-devices and denies physical devices unless explicitly allowed. `strict` permits only explicitly allowed accesses. `PrivateDevices=yes` is the stronger path because it also removes physical device nodes from the worker's `/dev`. [systemd.resource-control(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.resource-control.xml) [transient cgroup-property source](https://github.com/systemd/systemd/blob/v259.8/src/core/dbus-cgroup.c#L1510-L1595) |

[systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml) [transient supplementary-group source](https://github.com/systemd/systemd/blob/v259.8/src/core/dbus-execute.c#L2496-L2527) |

[systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml) [transient stdio source](https://github.com/systemd/systemd/blob/v259.8/src/core/dbus-execute.c#L2075-L2085) |

[systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml) [journal fields](https://github.com/systemd/systemd/blob/v259.8/man/systemd.journal-fields.xml) |

| `ProtectControlGroups=` | System-service setting only. | It is not available in an ordinary per-user unit. Do not add `Delegate=` to the worker merely to obtain cgroup access. `WatchdogSec=` is a service keep-alive timeout. systemd activates it after service startup, expects periodic `WATCHDOG=1` messages through `sd_notify()`, marks the service failed when the interval is missed, and terminates it with `SIGABRT` or the configured watchdog signal. It is not a per-callback deadline, and it is not the hardware watchdog configured by `RuntimeWatchdogSec=` in the system manager. [systemd.service(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.service.xml) [systemd-system.conf(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd-system.conf.xml)

The transient D-Bus parser in v259 accepts the needed service, execution, kill, and cgroup properties, including `MemoryMax`, `TasksMax`, `DevicePolicy`, `PrivateDevices`, `NoNewPrivileges`, `StandardOutput`, `StandardError`, `TimeoutStopUSec`, and `KillMode`. That establishes API support, not successful enforcement on every kernel or user-manager setup. [systemd transient service source](https://github.com/systemd/systemd/blob/v259.8/src/core/dbus-service.c#L850-L879) [systemd transient execution source](https://github.com/systemd/systemd/blob/v259.8/src/core/dbus-execute.c#L1860-L1879) [systemd transient stdio source](https://github.com/systemd/systemd/blob/v259.8/src/core/dbus-execute.c#L2075-L2085) [systemd transient execution restrictions](https://github.com/systemd/systemd/blob/v259.8/src/core/dbus-execute.c#L2274-L2293) [systemd transient cgroup source](https://github.com/systemd/systemd/blob/v259.8/src/core/dbus-cgroup.c#L453-L638) [systemd transient kill source](https://github.com/systemd/systemd/blob/v259.8/src/core/dbus-kill.c#L37-L76)

For this design, the settings that require system-manager authority are changing a user service to another UID, using system-only settings such as `ProtectControlGroups=` or `LogNamespace=`, and installing an authoritative parent-slice ceiling. The cgroup limits, kill settings, `NoNewPrivileges=`, journal stdio, and conditionally supported user namespaces can be requested by the user manager, subject to its delegated subtree and the host kernel. [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml) [systemd.resource-control(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.resource-control.xml) [system-only settings](https://github.com/systemd/systemd/blob/v259.8/man/system-only.xml) [user@.service(5)](https://github.com/systemd/systemd/blob/v259.8/man/user@.service.xml)

### User managers, D-Bus, and environment

PID 1 starts `user@UID.service`; the user manager then owns a hierarchy of units for that UID. User-manager processes are below `user@UID.service`, and all processes for one user are collected below `user-UID.slice`. Administrators can put resource drop-ins on `user-UID.slice`, `user-.slice`, or `user.slice`. [user@.service(5)](https://github.com/systemd/systemd/blob/v259.8/man/user@.service.xml)

The systemd Manager object is at `/org/freedesktop/systemd1`. It exposes `StartUnit`, `StopUnit`, `KillUnit`, `StartTransientUnit`, unit lookup, job objects, and unit properties. `StartTransientUnit()` returns the start-job object path; callers that need the actual result must observe the job result rather than treating the method return as proof that the process is ready. [org.freedesktop.systemd1](https://github.com/systemd/systemd/blob/v259.8/man/org.freedesktop.systemd1.xml)

State-changing calls to the system manager are protected by the `org.freedesktop.systemd1.manage-units` authorization path. A per-user supervisor should call its own user manager for its own worker units. Starting a system-manager unit instead would be a different privilege boundary and would require an administrator-authorized system service or polkit policy. [org.freedesktop.systemd1](https://github.com/systemd/systemd/blob/v259.8/man/org.freedesktop.systemd1.xml) [systemd Manager D-Bus source](https://github.com/systemd/systemd/blob/v259.8/src/core/dbus-manager.c#L1125-L1167)

The environment for a user-managed process generally includes the user manager's own environment. The user manager may receive additional variables from PAM and from a graphical session, but systemd describes that as typical rather than universal and recommends keeping the imported environment curated. A system-managed service does not automatically inherit the system manager's environment. [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml) [systemd(1)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.xml)

This is why the worker should be launched by the user manager as a service, not forked by the supervisor and attached to a scope. The service receives the user-manager environment without receiving the supervisor's caller environment or hardware descriptors. The latter still depends on the implementation not passing broker descriptors through socket activation, `ExecStart` file descriptors, or an inherited process fork. [systemd-run(1)](https://github.com/systemd/systemd/blob/v259.8/man/systemd-run.xml) [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml)

`NoNewPrivileges=` does not prevent the worker from asking the user manager or another D-Bus service to start a separate process. That new process belongs to the service requested over IPC, not to the worker's cgroup. [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml) [org.freedesktop.systemd1](https://github.com/systemd/systemd/blob/v259.8/man/org.freedesktop.systemd1.xml)

## Journal facts

`StandardOutput=journal` sends stdout to the journal, while `StandardError=journal` does the same for stderr. The routing choice is made by the manager context that owns the unit. It is not a switch that changes a user unit into a system unit or vice versa. [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml)

The journal records trusted fields for the system unit, user unit, cgroup, session, and owning UID. `journalctl --user` selects services of the current user, while `journalctl --system` selects system services and the kernel. A user unit therefore gives Lua output the required user-journal identity, and a system broker unit gives hardware errors the system-journal identity. [systemd.journal-fields(7)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.journal-fields.xml) [journalctl(1)](https://github.com/systemd/systemd/blob/v259.8/man/journalctl.xml)

Use the unit name as the stable worker identifier, for example `sliver-lua-worker-<generation>.service`. Use the unit's invocation ID when a second identity is needed for one runtime cycle. `_SYSTEMD_USER_UNIT` and `_SYSTEMD_OWNER_UID` are trusted journal fields; `SyslogIdentifier=sliver-lua` is only a human-readable stdout/stderr tag. [systemd.journal-fields(7)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.journal-fields.xml) [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml)

Do not use `LogNamespace=` to implement user/system separation. It creates a distinct journal namespace and data store, is system-service-only, and hides that output from ordinary `journalctl` unless the namespace is selected explicitly. [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml) [systemd-journald.service(8)](https://github.com/systemd/systemd/blob/v259.8/man/systemd-journald.service.xml)

A user can read their private per-user journal, but `journalctl --user` has a persistence requirement in the documented implementation. If issue #11 requires logs to survive reboot, Fedora packaging must verify the host's journald storage policy separately. [journalctl(1)](https://github.com/systemd/systemd/blob/v259.8/man/journalctl.xml) [systemd-journald.service(8)](https://github.com/systemd/systemd/blob/v259.8/man/systemd-journald.service.xml)

## Constraints

### A user unit is not an administrator-only policy boundary

A package can install a user-unit drop-in under `/etc/systemd/user`, and the dash-truncated drop-in path can apply to every generated worker name. The user unit search path also gives the user's own configuration directories higher priority than `/etc/systemd/user`. That means an administrator can provide and override the packaged default, but a user-manager drop-in is not an unoverrideable host policy against the account owner. [systemd.unit(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.unit.xml)

For an administrator-enforced ceiling, use a system-manager drop-in on `user-UID.slice` or `user@UID.service`. That ceiling applies to more than Sliver. A per-worker administrator-only ceiling would require a system-manager worker unit or a privileged broker API, which does not fit the accepted ordinary-user environment without more design work. Parent cgroup restrictions remain effective below the user manager. [user@.service(5)](https://github.com/systemd/systemd/blob/v259.8/man/user@.service.xml) [kernel top-down constraint](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#top-down-constraint)

### "All descendants" needs a precise boundary

`KillMode=control-group` and `cgroup.kill` cover the worker unit's cgroup tree. They do not cover a new service that the worker asks the user manager to create over D-Bus, nor a process started by another service such as `cron` or `at`. The accepted contract must define descendants as processes that remain in the worker unit cgroup, or it must give up unrestricted arbitrary IPC process-launch access. The current contract asks for ordinary D-Bus access, so the former definition is the compatible one. [systemd.kill(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.kill.xml) [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml) [org.freedesktop.systemd1](https://github.com/systemd/systemd/blob/v259.8/man/org.freedesktop.systemd1.xml)

### Hardware groups and hardware nodes are different controls

`PrivateDevices=` removes physical nodes from the worker's `/dev` and `DevicePolicy=closed` denies physical device access at the cgroup device filter. Neither setting literally edits the login user's supplementary group database. `SupplementaryGroups=` cannot subtract `video` or `input` if those groups arrive from the user's normal group membership. The user namespace implied by `PrivateDevices=` may make those host group IDs ineffective, but the exact `getgroups()` result and D-Bus credentials need Fedora testing. [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml) [systemd.resource-control(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.resource-control.xml)

`PrivateDevices=` does not by itself make sysfs backlight attributes read-only. `ProtectKernelTunables=yes` is the candidate systemd setting for that path, but the actual Asahi backlight file and the effect of the mount namespace must be tested. [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml)

### The application queue still needs its own bound

cgroup memory and task limits do not bound a Rust `Vec`, an IPC receive queue, a Unix socket payload, or a frame protocol's logical backlog. Issue #11 requires non-droppable input overflow to fail the worker without unbounded allocation. The current `TouchQueue` appends to a `Vec`, while the apply-request queue has a separate fixed capacity, so the new worker boundary must retain an explicit bounded input design. [Issue #11](https://github.com/wawow830/sliver/issues/11) [current touch queue](https://github.com/wawow830/sliver/blob/ad3725a/crates/sliverd/src/supervisor.rs#L30-L123)

### The memory budget needs a swap decision

`MemoryMax=512M` is the cgroup's `memory.max` limit. systemd exposes swap as a separate `MemorySwapMax=` policy. If the product means 512 MiB of combined memory and swap, implementation must set and test an explicit swap policy instead of treating `MemoryMax=` as that combined budget. [systemd.resource-control(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.resource-control.xml) [kernel memory interface](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#memory-interface-files)

### The system journal boundary requires separate processes

A worker launched as a user unit can put Lua stdout and stderr in the user journal. A hardware broker launched as a system unit can put DRM, evdev, uinput, and broker failures in the system journal. If the supervisor remains a user unit, its own `eprintln!` output is user-unit output by default; system failures that include the supervisor need a broker-owned logging endpoint rather than a different `StandardOutput=` value. [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml) [systemd.journal-fields(7)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.journal-fields.xml) [current supervisor logging](https://github.com/wawow830/sliver/blob/ad3725a/crates/sliverd/src/lib.rs#L72-L83)

## Concrete recommendation

### Use one transient user service per worker

Use the user manager's `org.freedesktop.systemd1.Manager.StartTransientUnit()` to start each candidate as a unique service named `sliver-lua-worker-<generation>.service`. Do not fork the worker from the supervisor and register a scope. The service topology gives systemd ownership of process creation, a separate cgroup, a manager-owned kill path, a clean user-manager environment, service identifiers, and journal routing. The transient unit remains disposable, while the common dash-truncated drop-in path gives administrators a policy hook. [systemd-run(1)](https://github.com/systemd/systemd/blob/v259.8/man/systemd-run.xml) [systemd.scope(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.scope.xml) [systemd unit source](https://github.com/systemd/systemd/blob/v259.8/src/core/unit.c#L5250-L5266) [systemd.unit(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.unit.xml)

The fixed baseline properties should be equivalent to the following service settings. These are implementation defaults, not a new Sliver configuration surface. In the transient D-Bus call, `GENERATED_TOKEN`, `UID`, and the source path are substituted into the `ExecStart` argument array by the supervisor.

```ini
[Service]
Type=exec
ExecStart=/usr/libexec/sliver-lua-worker --generation=GENERATED_TOKEN --source=/absolute/path --ipc=/run/user/UID/sliver/worker-GENERATED_TOKEN.sock

MemoryAccounting=yes
MemoryMax=512M
TasksAccounting=yes
TasksMax=64
OOMPolicy=kill

KillMode=control-group
TimeoutStopSec=1s
NoNewPrivileges=yes
PrivateDevices=yes
PrivateUsers=yes
DevicePolicy=closed
ProtectKernelTunables=yes

StandardInput=null
StandardOutput=journal
StandardError=journal
SyslogIdentifier=sliver-lua

Restart=no
WatchdogSec=0
```

`TimeoutStopSec=1s` in this example is only a finite systemd stop backstop. It is deliberately not the 500 ms Lua cleanup limit and not the two-second callback limit. The actual values should remain constants in the supervisor protocol and watchdog, not administrator-editable Lua settings. `OOMPolicy=kill` is included so a cgroup OOM failure does not leave a surviving descendant workload. [systemd.service(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.service.xml) [systemd.kill(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.kill.xml) [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml)

Leave `PrivateNetwork=`, `ProtectHome=`, `ProtectSystem=`, `PrivatePIDs=`, `PrivateIPC=`, and `DynamicUser=` disabled unless an integration test proves they preserve the accepted desktop contract. In particular, do not enable `PrivateNetwork=` or `ProtectHome=` for a worker that must use normal network, home, XDG runtime, D-Bus, and graphical-session resources. Do not enable `Delegate=` on the worker. [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml) [systemd.resource-control(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.resource-control.xml)

If the memory budget includes swap, add an explicit `MemorySwapMax=` value after deciding whether the intended policy is no swap or a combined budget. If the budget means cgroup RAM usage only, leave swap as an administrator policy and test the observed `MemoryCurrent` and `MemorySwapCurrent` values. [systemd.resource-control(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.resource-control.xml) [systemd cgroup interface](https://systemd.io/CONTROL_GROUP_INTERFACE)

### Keep Lua timeouts outside systemd service timeouts

The worker protocol should send a `CALLBACK_BEGIN` event before entering every Lua callback and `CALLBACK_END` after it returns. The external supervisor owns a monotonic two-second timer. A pure Lua loop, a blocking C module, a blocking process call, or a worker that stops heartbeating must cause the supervisor to call the user manager's `KillUnit()` with `SIGKILL`; it must not send the Lua `stop` callback first. This is the only design that can interrupt a callback that has stopped servicing its own command channel. `WatchdogSec=` is not a substitute because systemd's watchdog is a service keep-alive protocol based on `sd_notify(WATCHDOG=1)`, and it terminates a service for missed keep-alive messages rather than measuring an individual callback. [systemd.service(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.service.xml) [org.freedesktop.systemd1](https://github.com/systemd/systemd/blob/v259.8/man/org.freedesktop.systemd1.xml)

The planned cleanup path should be separate. On replacement, logout, or broker shutdown, send the explicit reason over the worker IPC and wait no longer than 500 ms for the Lua `stop` callback and worker acknowledgement. On success, stop the service and verify that its unit cgroup is empty. On timeout, disconnect, callback failure, or worker death, skip cleanup and issue the manager-owned `SIGKILL` to the whole unit cgroup. `TimeoutStopSec=` may handle an ordinary `StopUnit()` request, but it must not be the mechanism that enforces the Lua deadline. [systemd.service(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.service.xml) [systemd.kill(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.kill.xml) [systemd unit kill source](https://github.com/systemd/systemd/blob/v259.8/src/core/unit.c#L4130-L4170)

Do not implement Lua cleanup in `ExecStop=` or `ExecStopPost=`. systemd does not run `ExecStop=` when a service never started successfully, while `ExecStopPost=` is also invoked for failed starts and is intended for manager cleanup, not an untrusted Lua function. A failed candidate must be killed by unit name even if its start job failed partway. [systemd.service(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.service.xml)

### Make the systemd unit the descendant boundary

The supervisor must never pass DRM, evdev, uinput, or backlight descriptors to `ExecStart`. Give the worker only the control and frame IPC handles that the worker protocol needs, or have it connect to a private user-runtime socket by path. `StandardInput=null`, no socket activation, no `FileDescriptorStoreMax=`, and a service launch rather than a fork make accidental descriptor inheritance less likely. `PrivateDevices=yes`, `DevicePolicy=closed`, and `ProtectKernelTunables=yes` provide the device and sysfs checks that ordinary Unix group membership cannot provide on their own. [systemd-run(1)](https://github.com/systemd/systemd/blob/v259.8/man/systemd-run.xml) [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml) [systemd.resource-control(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.resource-control.xml)

The supervisor should use the user manager D-Bus API for `StartTransientUnit`, `StopUnit`, `KillUnit`, unit property reads, and job completion. It should not write `/sys/fs/cgroup` directly because the user manager is the systemd cgroup owner for the unit. It should not set `Delegate=` on the worker just to obtain a kill handle. [org.freedesktop.systemd1](https://github.com/systemd/systemd/blob/v259.8/man/org.freedesktop.systemd1.xml) [systemd resource control](https://github.com/systemd/systemd/blob/v259.8/man/systemd.resource-control.xml) [systemd control group delegation](https://systemd.io/CGROUP_DELEGATION)

### Give administrators a systemd-only override path

The supervisor should always send the baseline `MemoryMax=512M` and `TasksMax=64`, but it should expose no resource-limit option in Lua, TOML, IPC, or the public CLI. An administrator can change a scalar property for all generated worker names with a user-manager drop-in such as:

```ini
# /etc/systemd/user/sliver-lua-worker-.service.d/50-admin-limits.conf
[Service]
MemoryMax=768M
TasksMax=96
```

The prefix works because systemd searches dash-truncated drop-in names and because transient units accept drop-ins. A systemd daemon reload is required after installing or changing the drop-in. The user-manager path is an administrator configuration path, not a security boundary against the user who owns that manager. For a host-enforced upper bound, use a system-manager drop-in on `user-UID.slice`, accepting that it covers the user's other units too. [systemd.unit(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.unit.xml) [systemd unit source](https://github.com/systemd/systemd/blob/v259.8/src/core/unit.c#L5250-L5266) [user@.service(5)](https://github.com/systemd/systemd/blob/v259.8/man/user@.service.xml)

### Split journal ownership with the process split

The Lua worker should write `print()` output and Lua diagnostics to its own stdout and stderr. The user service's `StandardOutput=journal`, `StandardError=journal`, unit name, and `_SYSTEMD_USER_UNIT` field then make `journalctl --user-unit=sliver-lua-worker-...service` the normal query. The hardware broker should be a separate system service and write its failures to systemd's system journal. If supervisor failures must be system-journal records, send them through a broker-owned logging method instead of relying on the user service's stderr. [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml) [systemd.journal-fields(7)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.journal-fields.xml) [journalctl(1)](https://github.com/systemd/systemd/blob/v259.8/man/journalctl.xml)

## Topology comparison

| Topology | What it gives Sliver | Why it is or is not the choice |
| --- | --- | --- |
| Transient user service | A user-manager-created process, a distinct cgroup, clean service environment, service stop/kill semantics, cgroup resource settings, execution sandbox settings, transient identifiers, and user-journal routing. | Recommended. It supports overlapping staging and replacement through unique service names, and systemd v259 intentionally permits drop-ins for transient units. [systemd-run(1)](https://github.com/systemd/systemd/blob/v259.8/man/systemd-run.xml) [systemd unit source](https://github.com/systemd/systemd/blob/v259.8/src/core/unit.c#L5250-L5266) |
| Transient scope | A cgroup for externally forked processes and resource settings. | Reject. The worker would inherit the supervisor's process environment and any descriptors unless the supervisor sanitizes them. The scope cannot provide the service execution namespace needed for `PrivateDevices=`, `NoNewPrivileges=`, and the user-manager environment. [systemd.scope(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.scope.xml) [systemd-run(1)](https://github.com/systemd/systemd/blob/v259.8/man/systemd-run.xml) |
| Template user service | A persistent unit definition with a stable `sliver-lua-worker@.service.d` policy hook and disposable instances. | Viable alternative. It is easier to package and inspect, but it leaves a persistent template in the user's unit namespace. The transient service gives the same per-run identity without keeping instance definitions, while the dash-truncated drop-in path supplies the administrator hook. [systemd.service(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.service.xml) [systemd.unit(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.unit.xml) |
| Delegated child cgroup | Raw cgroup control for a supervisor-owned subtree, including direct use of cgroup files. | Reject for the worker. It gives the supervisor ownership below its unit, not systemd ownership of each worker. The worker would need manual process launch, descriptor scrubbing, namespace setup, journald routing, and kill-race handling. The delegatee can also change settings inside the delegated subtree, while only parent limits remain administrator-enforced. [systemd.resource-control(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.resource-control.xml) [kernel delegation model](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#delegation) |

A system-manager template or transient service under a dedicated non-hardware identity is the fallback if testing shows that a user unit cannot satisfy the literal supplementary-group requirement. It would make administrator policy authoritative, but it would no longer inherit the active user's user-manager environment automatically and would need an explicit design for home, XDG, graphical, and D-Bus access. [systemd.exec(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.exec.xml) [systemd.unit(5)](https://github.com/systemd/systemd/blob/v259.8/man/systemd.unit.xml)
